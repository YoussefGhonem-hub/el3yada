# el3yada app (Flutter)

One Flutter codebase for every platform. The full product spec is [`../spec.md`](../spec.md).

| Platform | Who can sign in |
|---|---|
| Android, iOS | Admin, doctor, assistant, patient |
| Windows, macOS | Admin, doctor, assistant (patients see "use the mobile app") |

The rule lives in [`lib/core/platform/app_platform.dart`](lib/core/platform/app_platform.dart) and is checked at sign-in and when a saved session is restored.

## Before the first run

1. **Flutter 3.50+** (`flutter --version`; CI uses 3.50.1). Upgrade with `flutter upgrade`.
2. **Windows desktop builds:** in the Visual Studio Installer, add the **"Desktop development with C++"** workload, including the MSVC build tools, C++ CMake tools and the Windows 10/11 SDK. Check with `flutter doctor`.
3. **Windows Developer Mode** (needed for plugins): `start ms-settings:developers`, then turn on Developer Mode.
4. **Android:** `flutter doctor --android-licenses` and accept them.
5. `flutter pub get`

## Run

There are two environments, `dev` and `prod`. Each has a config file in `config/`. Android also has a matching **flavor**: the `dev` app is called "el3yada dev", uses the ID `com.el3yada.app.dev`, and installs next to `prod`. Always pass the flavor and the config file together; the app refuses to start if they disagree. Windows has no flavors, so the config file decides.

```bash
# Dev: offline test accounts, no backend needed
flutter run --flavor dev --dart-define-from-file=config/dev.json   # Android
flutter run -d windows --dart-define-from-file=config/dev.json     # Windows

# UAT: the API that the "Deploy UAT" workflow publishes (http://amrsherif-002-site5.atempurl.com)
flutter run --flavor dev --dart-define-from-file=config/uat.json   # Android
flutter run -d windows --dart-define-from-file=config/uat.json     # Windows

# Prod builds (real API)
flutter build apk --flavor prod --dart-define-from-file=config/prod.json
flutter build windows --dart-define-from-file=config/prod.json
```

VS Code: the root `.vscode/launch.json` has a launch configuration for each environment on Android and Windows.

The UAT server has no HTTPS yet, so plain HTTP is allowed for that one host: on Android in the `dev` flavor only (`android/app/src/dev/res/xml/network_security_config.xml`), and on iOS in `ios/Runner/Info.plist` (`NSAppTransportSecurity`). Every other host still needs HTTPS. Remove both once UAT has a certificate, and the iOS one before the App Store.

iOS and macOS flavors need Xcode schemes (`dev`, `prod`), which can only be made on a Mac. Until then, run iOS and macOS without `--flavor`.

## Configuration

`config/dev.json` and `config/prod.json` are passed with `--dart-define-from-file`:

| Key | Meaning |
|---|---|
| `APP_ENV` | `dev` or `prod` |
| `API_BASE_URL` | The ASP.NET Core Web API |
| `USE_FAKE_AUTH` | Use the offline test accounts. Always off in `prod`. |

```text
    theme/app_theme.dart        Material 3 light/dark, colour tokens, breakpoints
    search/search_normalizer.dart  catalog search normalization (spec A.6)
    network/api_client.dart     dio + auth header + Accept-Language

    validation/validators.dart  Egyptian mobile and email rules (spec section 11)
    widgets/                    shared widgets (language and theme switches)
  features/
    auth/                       sign-in (domain, data, application, presentation)

    admin_support/              AD11 accounts support, AD12 deletion requests (Phase 4)
    shell/                      per-role navigation and adaptive layout
  l10n/
    app_en.arb, app_ar.arb      every user-facing string
    gen/                        generated by `flutter gen-l10n`

```

Each feature follows the same layers: `domain/` (models), `data/` (API), `application/` (Riverpod controllers), `presentation/` (screens).

## Talking to the API

- Each feature has a repository interface in `data/` with two implementations: `Api…Repository` (dio, `/api/...` routes) and `Fake…Repository` (offline data). Dev builds with `USE_FAKE_AUTH` use the fakes, because their tokens aren't real; prod always uses the API.
- API failures become `ApiError` with the server's `code` (`core/network/api_error.dart`); `l10n.apiErrorMessage(error)` gives the message. Add new codes there.
- Stored files (attachments, prescription PDFs) are fetched with the user's token and kept in memory for a few minutes (`fileBytesProvider`). Never build public file URLs.
- `test/fixtures/patient/*.json` are real responses of the API's demo data. `patient_models_test.dart` parses them, so a change on either side that breaks the contract fails a test. Refresh them after changing an endpoint (backend/README.md, "Demo data and tokens").

## Conventions

- **Strings:** never hard-code text. Add the key to both `app_en.arb` and `app_ar.arb`, then run `flutter gen-l10n` (it also runs on build).
- **Colours:** never hard-code colours. Use `Theme.of(context).colorScheme` or `context.el3yadaColors` (examination, consultation, allergy, attention). The palette comes from the chosen design: pine `#0F4C45`, mint ground `#E6F2EC`, mint `#7CE0C3`, coral `#FF6B5A` for "new" dots, ink `#12312C`. Dark mode has its own tokens in `AppTheme.darkScheme`.
- **Font:** Alexandria, bundled in `assets/fonts/` (Arabic and Latin). Arabic text in PDFs uses Noto Sans Arabic instead, because the PDF library needs glyphs Alexandria lacks (see `test/prototypes/font_coverage_test.dart`).
- **Search:** catalog and picker search use `package:catalog_core` (`../packages/catalog_core`), the same normalization the catalog builder indexes with (spec A.6). `core/search/search_normalizer.dart` re-exports it; never write a second normalizer.

### Prescription PDFs

- **Who builds them:** the doctor's app, in `features/prescriptions/pdf/rx_pdf.dart` (spec 6.4.1), and uploads the PDF when sending. Every reprint prints that stored PDF, so the paper and the patient's copy always match (BR-RX5).
- **Fonts:** the PDF copy of Noto Sans Arabic gets a compact line box (`RxPdfFonts.compactLineMetrics`); its own 2.11 em line height doesn't fit the A5 layout. Fonts are subset: an A5 prescription without logo and signature is about 200 KB, and the 1000 px PNGs add their own size.
- **Print all:** the `pdf` package can't merge PDFs, so the session's stored PDFs are rasterized at 300 dpi (`Printing.raster`) and placed one per page in a single print job (`combineForPrint`).
- **Checking the layout:** `EL3YADA_SCREENSHOTS=1 flutter test test/screenshots/phase3_prescriptions_screens_test.dart` also writes sample PDFs (A5 Arabic, 12 items on two pages, English, a request, pre-printed paper, A4) to `build/screenshots/`. AC-15 still needs a print on a real printer.
- **API models:** freezed + json_serializable, like `AuthSession`. After changing a model, run `dart run build_runner build` and commit the generated `*.freezed.dart` and `*.g.dart` files. CI fails if they are out of date.
- **Layout:** below 600 px wide is phone (floating bottom bar), 600–1024 is tablet (rail), and 1024+ is desktop (side menu). See `RoleScaffold`. On phones the body runs behind the bar (`extendBody`): lists get the bar's height from `MediaQuery` padding, so don't set a fixed bottom padding on a list without adding `MediaQuery.paddingOf(context).bottom`.
- **Screens:** every screen has an ID in `spec.md` (D34, AS1, P1, AD1 …). Placeholder pages show it until the screen is built.

### Motion

- **Tokens:** every duration and curve comes from `Motion` in `lib/core/theme/motion.dart`: `fast` 150 ms (press, toggles), `normal` 250 ms (state changes, nav bar), `slow` 400 ms (screen entrances, signature moments), `fastExit` / `normalExit` / `slowExit` (about 65%), `enterCurve`, `exitCurve`, `exitCurveReversed` (for `switchOutCurve` and `reverseCurve`), `standardCurve`, `spring`, `springBouncy`. Never type a `Duration` or a curve in a widget.
- **Reduced motion:** read `Motion.of(context).reduced` (it comes from `MediaQuery.disableAnimations`). When it is on, entrances and decoration become a plain fade or nothing; state changes still crossfade. The shared widgets below already do this.
- **Performance:** animate transform and opacity only, and put a `RepaintBoundary` around anything that animates continuously (shimmer, spinners, Lottie).
- **Page transitions:** nothing to add per route. A `GoRoute` with `builder:` slides on the horizontal shared axis (mirrored in Arabic) through `AppPageTransitionsBuilder` in the theme. Each menu destination is a branch of its role's `StatefulShellRoute`, so tabs fade through and keep their state. Put detail screens under their tab's `GoRoute` (`routes: [...]`).
- **Nav badges:** override `navBadgeProvider` (in `role_scaffold.dart`) to return `NavBadge.count(n)` or `NavBadge.dot()` for a destination path; the bar, rail and side menu show it, and "More" gets a dot when something inside it has one.

| Widget (`lib/core/widgets/`) | Use it for |
|---|---|
| `Pressable(onTap:, child:)` | Custom tappable cards and tiles: scales to 0.97 on press. Buttons and `InkWell` already ripple. |
| `StaggerGroup` + `StaggeredEntrance(index:, child:)` | List and grid items that fade and rise in, 40 ms apart (first 8 only). |
| `SkeletonLoading(loading:, child:)` | Loading lists and cards: wrap the real widget built with placeholder data. No centred spinners. |
| `EmptyState(title:, message:, actionLabel:, onAction:)` | Empty lists: illustration, message and the action that fills it. |
| `SuccessCheck(onCompleted:)` | The success moment (P15, D15, D20): the Lottie check, 1.1 s. |
| `StateSwitcher(state:, …)` / `AsyncStateSwitcher(value:, …)` | Crossfading loading, content, empty and error. |
| `SubmitButton(label:, status:, onPressed:)` | Form submit: label → progress (after 300 ms) → check. |
| `ShakeOnError(trigger:, child:)` | Shake a form once when `trigger` changes (pass an error counter). |
| `ContainerTransform(closedBuilder:, openBuilder:)` | List → detail: the card grows into the screen. |
| `AppLogoMark(animate: true, hero: true)` | The logo drawing itself (splash), with `AppLogoMark.heroTag` for the splash → login flight. |
| `navigation/`: `FloatingNavBar`, `AppNavRail`, `AppSideMenu` | Used by `RoleScaffold`; the same sliding indicator in all three. |

- **Lottie:** files live in `assets/lottie/`, 100 KB and 1.5 s at most. Record the source and licence of each in `assets/lottie/SOURCES.txt`, and replace its colours with theme colours through `LottieDelegates` (see `SuccessCheck`).
- **flutter_animate:** fine for one-off effects, but its `Animate` widget starts a timer even with no delay, so a widget test that builds it must end with `pumpAndSettle()` or a timed `pump`. The shared widgets above use Flutter's own animations and don't have this catch.
- **Tests:** `test/support/harness.dart` pumps a widget in the app theme, in Arabic (`rtl: true`) or with reduced motion (`reduced: true`).

## iOS: TestFlight

No Mac is needed. The `iOS TestFlight` workflow (`.github/workflows/ios-testflight.yml`) builds the app on a GitHub Mac, signs it and uploads it to App Store Connect.

**Deploy = push to `uat`.** Every push to the `uat` branch that changes `app/`, `packages/` or the workflow deploys a new TestFlight build. The app's analyze and tests run first on Linux, and the Mac build starts only if they pass. Work still happens on `dev`; when a version is ready for testing:

```bash
git checkout uat
git merge --no-ff dev
git push origin uat
```

It can also be started by hand: Actions tab > iOS TestFlight > Run workflow, or `gh workflow run "iOS TestFlight" --ref dev -f config=demo`. GitHub shows that button only once the workflow file is on `main`.

- A push to `uat` builds against the UAT API (`config/uat.json`). The same push runs "Deploy UAT" when `backend/` changed, so the API and the app go out together.
- `config=uat` (the default by hand too) builds with `config/uat.json`.
- `config=demo` builds with `config/dev-offline.json`: the offline test accounts, no server needed.
- `config=prod` builds with `config/prod.json`. It refuses while that file still points at `api.example.com`.
- The build number is the workflow's run number, so every run uploads a new build. The version comes from `pubspec.yaml`.
- A run takes about 20 to 30 minutes. GitHub counts Mac minutes at 10 times the Linux rate on the free plan, so push to `uat` only when there is something to test, not after every commit.

### One-time setup

1. **App Store Connect API key.** App Store Connect > Users and Access > Integrations > App Store Connect API > Team Keys > Generate. Role: **App Manager**. Download `AuthKey_<KEY_ID>.p8`; Apple allows only one download, so keep it safe. Note the **Key ID** and the **Issuer ID** shown above the list.
2. **Certificate private key.** Make a new RSA key on any computer (Git Bash works on Windows):
   ```bash
   ssh-keygen -t rsa -b 2048 -m PEM -f ios_distribution_private_key -q -N ""
   ```
   Keep the file safe. The first workflow run makes a distribution certificate from it, and later runs need the same key to reuse that certificate.
3. **Repository secrets.** GitHub > Settings > Secrets and variables > Actions > New repository secret:

   | Secret | Value |
   |---|---|
   | `APP_STORE_CONNECT_ISSUER_ID` | The Issuer ID |
   | `APP_STORE_CONNECT_KEY_IDENTIFIER` | The Key ID |
   | `APP_STORE_CONNECT_PRIVATE_KEY` | The whole `.p8` file, including the BEGIN and END lines |
   | `CERTIFICATE_PRIVATE_KEY` | The whole `ios_distribution_private_key` file, including the BEGIN and END lines |

   Or from Git Bash: `gh secret set APP_STORE_CONNECT_PRIVATE_KEY < AuthKey_XXXX.p8` and `gh secret set CERTIFICATE_PRIVATE_KEY < ios_distribution_private_key`.
4. **Testers.** App Store Connect > the app > TestFlight > Internal Testing > add a group and its testers. Each new build reaches them after Apple processes it.

Never commit the `.p8` file or the certificate key.
